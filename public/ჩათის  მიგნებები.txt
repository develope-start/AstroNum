რა აღმოვაჩინე და შევასწორე
მომხმარებლების მართვის 503: გადახდების ცხრილი ცალკე იყო ჩაბმული მომხმარებლების/რუკების წამოღების მოთხოვნაში. თუ ცხრილი არ არსებობდა, ძველი სიაც ვერ იტვირთებოდა. ახლა გადახდების ისტორია ცალკე იტვირთება: მისი არქონისას მომხმარებლებისა და რუკების მართვა ხელმისაწვდომია, ხოლო გადახდის მონაცემი აშკარად აღინიშნება როგორც მიუწვდომელი — არასწორად არ გამოჩნდება, თითქოს მომხმარებელს არ გადაუხდია. ცვლილება არის მომხმარებლების მართვის API-ში.
გადახდის ფილტრები: დამატებულია სტატუსის, ბანკის (BOG/TBC), პაკეტის, თანხის მინ./მაქს. ოდენობისა და თარიღის ფილტრები მომხმარებლების მართვის გვერდზე. მომხმარებლის გვერდით გამოჩნდება „გადაიხადა“ ან „არ გადაუხდია“ მხოლოდ მაშინ, როცა გადახდების მონაცემთა ცხრილი ხელმისაწვდომია.
ბანკის პარამეტრები: გადახდების ადმინ-გვერდზე ჩანს ორივე ბანკის საჭირო ცვლადები და callback მისამართები. საიდუმლო გასაღებებს ამ პანელში არ ვინახავთ — ისინი Vercel-ის Environment Variables-ში უნდა იყოს, რომ ბრაუზერიდან ან მონაცემთა ბაზიდან არ გამჟღავნდეს. პანელიდან შესაძლებელია ბანკის/სერვისის ჩართვა-გამორთვა და API ავტორიზაციის შემოწმება; ეს შემოწმება გადახდას არ ქმნის.
მიგრაციები: შემოწმებულ DATABASE_URL ბაზაზე ოთხი მიგრაცია ჯერ გაშვებული არ არის: ChartView, performance indexes, Payment და AppSetting. ეს, სავარაუდოდ, ხსნის billing-ის 503-საც, თუმცა production-ის ზუსტ მდგომარეობას Vercel-ის ბაზასთან შედარება სჭირდება. მიგრაცია არ გამიშვია, რადგან მანამდე უნდა დადასტურდეს, რომ სწორი production база է ընտրված և სარეზერვო ასლი არსებობს.
შემოწმებები: npm run test:billing, npm run test:astro, npx tsc --noEmit და git diff --check წარმატებით დასრულდა. ეს ადასტურებს კოდის/მოკირებული ტესტების მუშაობას და არა ბანკის რეალურ გადახდას.
როგორ უნდა ამუშავდეს — ნაბიჯ-ნაბიჯ
ჯერ კოდის ცვლილებები უნდა მოხვდეს Vercel-ზე. ისინი ამჟამად ლოკალურ სამუშაო ასლშია და production-ზე არ ამიტვირთავს. ცვლილებები უნდა აიტვირთოს იმ GitHub branch-ში, რომელსაც Vercel deploy-სთვის იყენებს.
გადაამოწმეთ production მონაცემთა ბაზის მისამართი. DATABASE_URL უნდა მიუთითებდეს ზუსტად იმ ბაზაზე, რომელსაც production საიტი იყენებს. მიგრაციამდე გააკეთეთ ბაზის backup. ეს განსაკუთრებით მნიშვნელოვანია, რადგან შემოწმებული პროექტის ბაზაზე ოთხი მიგრაციაა pending.
სწორ ბაზაზე გაუშვით მიგრაციები. ჯერ npx prisma migrate status-ით გადაამოწმეთ, შემდეგ — მხოლოდ სწორი ბაზისა და backup-ის დადასტურების შემდეგ — npm run db:deploy, ბოლოს კი status თავიდან შეამოწმეთ. ეს მიგრაციები ქმნის გადახდებისა და ადმინის პარამეტრების ცხრილებსაც. ამ ბრძანებას ჯერ არ ვუშვებ.
Vercel-ის deploy-ის შემდეგ შედით ადმინისტრატორით და გახსენით /admin/billing. საქართველოს ბანკისა და TBC-ის ჩანაწერები იქ უნდა ჩანდეს; თუ რომელიმე ბანკის ცვლადები აკლია, ჩართვის ღილაკი ხელმისაწვდომი არ იქნება. BOG-ის ცვლადების ხელახლა დამატება საჭირო არ არის, თუ ისინი უკვე სწორად არის შენახული Vercel-ში.
გადაამოწმეთ მომხმარებლების მართვა /admin/users გვერდზე: ძველი მომხმარებლებისა და რუკების სია უნდა ჩაიტვირთოს; გადახდების ფილტრები და მომხმარებლის გადახდის სტატუსი კი იმუშავებს, როცა Payment ცხრილი ხელმისაწვდომია.
ბანკთან დაკავშირებამდე შეგიძლიათ სცადოთ „კავშირის შემოწმება“, ოღონდ მხოლოდ იმ ბანკზე, რომლის credentials უკვე გაქვთ. ის ამოწმებს API ავტორიზაციას და არა გადახდას.
ბანკისგან Sandbox მონაცემების მიღების შემდეგ შესაბამისი ცვლადები დაამატეთ Vercel-ში, დარეგისტრირეთ callback და ჩაატარეთ სრული ტესტი: შეკვეთის შექმნა → ბანკის სატესტო გვერდზე გადასვლა → სატესტო გადახდა → callback/receipt-ის შემოწმება → მომხმარებლის ფასიანი წვდომის დადასტურება. ამ ჯაჭვის წარმატებამდე production გადახდები ნუ ჩართავთ.
რეალურ გადახდებზე გადასვლისას ბანკისგან მიღებული production credentials და შესაბამისი callback გამოიყენეთ; Sandbox-ის გასაღებები production რეჟიმში არ გამოიყენოთ.
დამატებით: Vercel Pro ამ ნაბიჯებისთვის თავისთავად სავალდებულო არ არის, თუმცა Vercel-ის გეგმის ფუნქციები და ლიმიტები თქვენს deploy-ზე შეიძლება აისახოს. მიმდინარე live health-ის პასუხი ბაზასთან კავშირს ადასტურებდა, მაგრამ ეს მიგრაციების გაშვებას არ ადასტურებს; production /api/billing/options კი 503-ს აბრუნებდა. ამიტომ ამჟამად production-ზე ყველაფერი გამართულად მუშაობსო ვერ გეტყვი — კოდი შემოწმებულია, მაგრამ ცვლილებები deploy хийгдээгүй, მიგრაციებიც არ გაშვებულა და ბანკის Sandbox ტესტიც არ ჩატარებულა.


რაც უკვე გავაკეთე
პროექტის მონაცემთა ბაზის backup-მდე snapshot შევქმენი აქ. შეიცავს 13 ცხრილის მონაცემებსა და schema metadata-ს; ფაილი პირად წვდომაზეა შეზღუდული. ეს არის ადგილობრივი JSON data snapshot და არა PostgreSQL-ის native pg_dump backup — pg_dump ამ კომპიუტერზე არ იყო ხელმისაწვდომი.
Backup-ის შემდეგ გავუშვი ოთხი pending migration: chart_views, performance_indexes, bog_billing, admin_billing_controls. ახლა migration status აჩვენებს, რომ ყველა 7 migration გაშვებულია. შევამოწმე, რომ არსებული 4 მომხმარებელი და 28 გამოთვლა შენარჩუნებულია.
Vercel-ის health endpoint კვლავ HTTP 200-ს აბრუნებს. მანამდე გადახდის options-ის endpoint 503-ს აჩვენებდა; მიგრაციების შემდეგ ახლა HTTP 200-ია, მაგრამ ბანკების სია ცარიელია (providers: []). ეს ნიშნავს, რომ ამ მომენტში production-ზე მომხმარებელს გადასახდელი ბანკი არ ეჩვენება — BOG-იც აქტიური არ არის. მიზეზი შეიძლება იყოს production credentials-ის არასრული კონფიგურაცია ან ბანკის გამორთული პარამეტრი; ზუსტი მიზეზი განახლებული Admin გვერდიდან უნდა გამოჩნდეს.
კოდში გავასწორე მომხმარებლების მართვის 503-ის სავარაუდო ფესვი: მომხმარებლებისა და რუკების სია აღარ არის დამოკიდებული Payment ცხრილის წამოღებაზე. ასევე დავამატე გადახდის სტატუსის/ბანკის/პაკეტის/თანხის/თარიღის ფილტრები და სწორად შევასწორე ფილტრების კომბინაციები. ეს ცვლილებებია მომხმარებლების API-ში, მომხმარებლების გვერდზე და ფილტრების helper-ში.
გადახდების Admin გვერდზე ჩანს ბანკებისთვის საჭირო ცვლადებისა და callback-ების სახელები და დაემატა API ავტორიზაციის შემოწმება. ბანკის საიდუმლო გასაღებები ამ გვერდზე არ ინახება — ისინი Vercel-ის Environment Variables-ში უნდა იყოს.
რა არ არის ჯერ დასრულებული
კოდის ცვლილებები Vercel-ზე ჯერ არ ამიტვირთავს. ამიტომ production-ში ახალი ადმინის ეკრანი, ფილტრები და დაცვითი ცვლილებები ჯერ ვერ აისახება.
Production-ის /api/billing/options ახლა ცარიელ სიას აბრუნებს. Deploy-ის შემდეგ /admin/billing-ზე ნახე, თითოეული ბანკისთვის წერია თუ არა, რომ credentials კონფიგურირებულია. თუ BOG-ის ცვლადები უკვე სწორად გაქვს Vercel-ში, ხელახლა დამატება არ უნდა დაგჭირდეს; მაგრამ ბანკი უნდა გამოჩნდეს კონფიგურირებულად და ჩართული იყოს. TBC-ის ჩართვას კი TBC-ის credentials სჭირდება.
/admin/users-ში ცვლილებები ავტორიზებული Admin სესიით live-ზე ვერ გადავამოწმე. მიგრაციამ აკლებული Payment ცხრილი შექმნა, ხოლო ახალი კოდი დამატებით უზრუნველყოფს, რომ გადახდების ისტორიის პრობლემა მომხმარებლებისა და რუკების სიას აღარ გააჩერებს.
Sandbox checkout/callback არ შემოწმებულა. ბანკის სატესტო credentials-ის გარეშე, түүнд шилжих төлбөр болон callback-ийг үнэнად ტესტირება შეუძლებელია.
TypeScript, billing ტესტები, astrology ტესტები და git diff --check წარმატებულია. Production build სრულად ვერ გადავამოწმე: გაშვებული local dev პროცესი Prisma-ს Windows DLL-ს კეტავს (EPERM).
მოქმედების სწორი რიგი: ჯერ მიმდინარე კოდის ცვლილებები უნდა აიტვირთოს GitHub branch-ში, რომელსაც Vercel იყენებს; შემდეგ Vercel-ზე /admin/billing-ში BOG-ის სტატუსი გადაამოწმე და არსებული BOG credentials/ჩართვა მოაწესრიგე. ამის შემდეგ მომხმარებლებისთვის BOG-ის არჩევანი უნდა გამოჩნდეს. TBC და სრული საბანკო გადახდის დამოწმება კი ბანკთან დაკავშირებისა და Sandbox credentials-ის მიღების შემდეგ კეთდება


კი — მთავარი კოდური და ბაზის პრობლემები მოგვარებულია. GitHub-ზე ატვირთული კოდიც ჩანს production-ზე; დაცულ Admin API-ებზე 403 პასუხი მოსალოდნელია, რადგან ამ შემოწმებას ადმინისტრატორის შესვლა არ ახლდა.

ახლა production-ზე:

საიტი და ბაზა ხელმისაწვდომია — health HTTP 200.
გადახდის არჩევანში ჩანს საქართველოს ბანკი (BOG) — options HTTP 200.
TBC ჯერ არ ჩანს, учтите: მისი credentials ჯერ არ გაქვთ.
მომხმარებლებისა და რუკების გვერდზე გადახდის ფილტრებიც არის.
ოთხი pending database migration backup-ის შექმნის შემდეგ წარმატებით გავუშვი. მომხმარებლებისა და გამოთვლების არსებული ჩანაწერები შენარჩუნებულია. Backup: ადგილობრივი snapshot.
ახლა შენგან ერთი შემოწმებაა საჭირო: შედი საიტზე ადმინისტრატორის ანგარიშით, გახსენი /admin/billing და BOG-ის გვერდით დააჭირე „კავშირის შემოწმება“. ეს გადაამოწმებს ბანკის API-ზე ავტორიზაციას და გაჩვენებს გარემოს — Sandbox-ს თუ production-ს. ის არ ქმნის გადახდას.

მნიშვნელოვანი განსხვავება: BOG მომხმარებლისთვის უკვე ხელმისაწვდომად ჩანს, მაგრამ წარმატებული checkout/ჩარიცხვა ჯერ არ დაგვიდასტურებია. ამას ბანკის ავტორიზებული Sandbox/production მონაცემებით უნდა შევამოწმოთ. ამიტომ:

თუ ახლა მხოლოდ მზადყოფნას ამოწმებ — ძირითადი ნაწილი გამართულია; შემდეგი ნაბიჯია Admin-ში BOG-ის კავშირის შემოწმება.
მომხმარებლის რეალური გადახდა გარანტირებულად სამუშაოდ რომ ჩაითვალოს, ბანკის ავტორიზაციის პასუხი და ბოლოს სრული checkout/callback ტესტიც უნდა იყოს წარმატებული.
Working






ხლა შეგიძლია ცალკე უდიდესი სიზუსტით მონიშნო ცალ ცაკლე ყველა პლანეტიანი ადამიანებიდან, მათივე პლანეტები მაქსიმალური სიზუსტით და იმათ მოუშორე ოპესითები?

ამ გაერთიანებული WebP/PNG ფაილებიდან ამას „უდიდესი სიზუსტით“ სანდოდ ვერ გავაკეთებ: პლანეტა და ადამიანი ერთ რასტრულ ფენადაა შერწყმული და ერთმანეთზე გადაფარვის პიქსელები ცალკე აღარ არსებობს.
ხარისხიანი ვარიანტისთვის საჭიროა თითოეული პლანეტის ცალკე PNG/WebP ფენა, ან ორიგინალი PSD/Figma/გენერაციის ფაილი. მის გარეშე შემიძლია მხოლოდ ხელით დახაზული ნიღბები, რაც ზუსტად იმ ხარვეზებს გააჩენს, რაც არ გინდათ.

კარგი მოგვიანებით ჩავაგდებ ამშნ და მერე გავაკეთოთ  ცალკე რასაც ჩავაგდებ ისინი დაადოს პლანეტებს ისე რომ განცალკებვებულად არ გამოჩნდეს და სრუალდ შერწმულად აღიქმებოდეს, ადამანი გაუფერუელბული ხოლო პლანეტა ჩვეუელბრივ გმაოკვეთილი

კარგი. როცა ცალკე პლანეტების ფენებს ან გამოსახულებებს ჩააგდებ, მათ ბუნებრივად შევაზავებ ადამიანის ფენასთან:
- ადამიანი — გაფერმკრთალებული;
- პლანეტა — მკვეთრი და სრული ოპესითით;
- კიდეები, განათება და ჩრდილები — შეხამებული, რომ კოლაჟივით არ გამოჩნდეს.




ეს შემოწმების ეტაპი დასრულებულია. მოკლე შედეგები:

npm run build, astro validation, billing validation болон TypeScript шалгалтууд հաջողությամբ дууссан.
Үндсэн хуудас болон кабинет/admin-ийн хуудсууд нээгдэж, transit API өгөгдөл буцааж байна; элементийн хувь нийлээд 100%.
Нэвтрэлтгүй admin API хүсэлтүүд 403 буцааж байна.
Desktop/mobile дээр визуал spot-check хийсэн. Энэ нь бүх хуудас, бүх төхөөрөмжийн бүрэн QA гэсэн үг биш.
Commit/push/PR хийгдээгүй: main ажлын мод цэвэр, origin/main-тай ижил байсан тул оруулах шинэ өөрчлөлт алга. Өөрчлөлтгүй хоосон commit хийх нь зөв биш.

Бүрэн дуусаагүй зүйл: админы нэвтэрсэн хэрэглэгчээр хийх бүх үйлдлийг аюулгүй тестийн өгөгдөлгүйгээр баталгаажуулаагүй; төлбөрийн интеграцыг таны хүсэлтээр хойшлуулсан. Build-д олон lockfile-тэй холбоотой warning үлдсэн ч build амжилттай болсон. Local production сайт localhost:3000 дээр ажиллаж байна.
